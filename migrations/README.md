# SQL-миграции

Здесь будут изменения прикладной схемы PostgreSQL. Сейчас SQL-файлов нет:
модель пользователя ещё не определена. Пустой каталог — успешный запуск
с результатом `0 applied`, без создания таблицы версий.

## Запуск

Из корня репозитория, при запущенной PostgreSQL:

```powershell
go run ./cmd/migrate up
```

Команда читает `.env` и использует те же `POSTGRES_*`, что и HTTP-сервер.
Окружение имеет приоритет над `.env`. Подключение ограничено 5 секундами,
контекст подключения и применения миграций — одной минутой.
`Ctrl+C` отменяет операции; освобождение advisory lock выполняется отдельно
от отменённого контекста, поэтому завершение процесса может занять больше времени.
HTTP-сервер автоматически миграции не запускает.

## Правила

- Имя: `00001_create_users.sql`, затем `00002_...sql`. Номера уникальны
  и возрастают; номер миграции не связан с номером коммита.
- Файл начинается с `-- +goose Up`, далее обычный SQL.
- Отсутствующий каталог и неверное имя SQL-файла считаются ошибкой,
  чтобы опечатка не выглядела успешным запуском без изменений.
- Каждая миграция выполняется в отдельной транзакции вместе с записью
  её версии в `goose_db_version`. При ошибке текущая миграция откатывается,
  ранее завершённые остаются применёнными.
- Повторный `up` пропускает уже выполненные версии. Goose не проверяет
  изменения содержимого выполненных файлов: их не редактируем, добавляем новый.
- PostgreSQL advisory lock защищает от двух одновременных запусков этой команды
  в одной базе. Соединение должно идти напрямую в PostgreSQL, без
  transaction-pooling proxy.
- Пока поддерживается только `up`. Изменения исправляем новой миграцией;
  потенциально разрушительный автоматический `down` не добавлен.
- SQL, который нельзя выполнять в транзакции, требует отдельного решения.
  `NO TRANSACTION` без разбора гарантий не используем.

## Проверка на отдельной базе

Оба набора integration-тестов используют отдельную базу. Создайте пустую
`chat_test` в development PostgreSQL (один раз; если она уже есть, пропустите):

```powershell
docker compose --env-file .env -f docker/docker-compose.dev.yml exec postgres createdb -U chat chat_test
```

Если меняли `POSTGRES_USER` или имя тестовой базы, замените аргументы команды.
Добавьте в корневой `.env` имя **тестовой** базы:

```dotenv
POSTGRES_TEST_DB=chat_test
```

Адрес, порт, пользователь, пароль и SSL-режим берутся из тех же `POSTGRES_*`,
что и у приложения. Второй URL с копией пароля больше не используется.
Помощники в `tests/integration/testdb_test.go` читают корневой `.env` независимо от
рабочей директории, в том числе при запуске из GoLand. Окружение имеет приоритет над
файлом, даже если значение пустое. `POSTGRES_TEST_DB` обязателен, должен
оканчиваться на `_test` и отличаться от `POSTGRES_DB`.

```powershell
go test ./...
go test -tags=integration -v -count=1 ./tests/integration
go vet ./...
go vet -tags=integration ./tests/integration
```

При отсутствующей или неверной настройке integration-тесты завершаются
ошибкой конфигурации, а не пропускаются. Каждый миграционный сценарий создаёт отдельную
случайную схему и удаляет только её. Тесты проверяют применение, повторный
запуск, одновременные запуски, откат ошибочной миграции и успешный повтор после исправления.
Их SQL существует только в тестовых фикстурах, а не в прикладной схеме.
Тест подключения PostgreSQL делает только `SELECT 1` и проверяет закрытие пула
в той же тестовой базе. Development-база не используется.

`go test ./...` запускает unit- и компонентные тесты без PostgreSQL.
Integration-тесты расположены отдельно в `tests/integration` и включаются тегом
`integration`. Вся их вспомогательная логика находится в `*_test.go`.

Реальное изменение схемы через CLI можно проверить на `chat_test`, временно
задав `$env:POSTGRES_DB = 'chat_test'` и положив тестовый SQL в `migrations/`.
После проверки удалите только созданный вами пробный файл и верните окружение.
Не переносите пробные миграции в development-базу и не коммитьте их.

## Зависимость

Используется библиотека [pressly/goose](https://github.com/pressly/goose),
версия зафиксирована в `go.mod`. CLI goose с драйверами других СУБД не подключён.
Лицензия MIT допускает бесплатное использование и распространение с сохранением
copyright и [текста лицензии](https://github.com/pressly/goose/blob/v3.30.1/LICENSE).
При подготовке распространяемых бинарников или Docker-образов нужно включить
лицензии используемых зависимостей в состав релиза; отдельный каталог
с копиями лицензий в репозитории для этого не обязателен.
