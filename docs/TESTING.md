# Тестирование

Команды выполняются из корня репозитория.

## Unit- и компонентные тесты

Находятся рядом с проверяемым кодом и не требуют PostgreSQL:

```powershell
go test ./...
```

Unit-тесты проверяют валидацию, регистрацию, вход, выход, создание и проверку
сессий, Argon2id, передачу контекста и обработку ошибок. Зависимости service
подменяются небольшими fake-реализациями без SQL-моков.

Компонентные HTTP-тесты проверяют JSON, cookies, статусы ошибок, защиту от
межсайтовых запросов и доступ только к собственному профилю. Ограничитель
запросов проверяется на сброс окна, независимость IP и маршрутов,
очистку и предел таблицы, конкурентный доступ и ответ `429` с `Retry-After`.
На уровне HTTP-цепочки проверяется, что превышение лимита не вызывает service,
а запросы, отклонённые защитой от чужого origin, не расходуют лимит.

Для фото проверяются форматы и размеры, обрезка и масштабирование, прозрачность,
отмена контекста, замена и удаление файлов, отказы БД и хранилища.
Компонентные HTTP-тесты проверяют бинарные ответы PNG, ограничения тела,
запрет изменения чужого фото и доступ к чтению с действующей сессией.
Файловые тесты используют временные каталоги. Защита от выхода через ссылку
проверяется junction на Windows и symlink на остальных платформах;
права на создание Windows symlink для этого не нужны.

Отдельно проверяются преобразование пользователя в DTO, точный состав JSON
и перевод дат в UTC, граница тела запросов 4096/4097 байт, отказ запуска
на занятом порту и освобождение listener при отменённом подключении к БД.

## Подготовка integration-тестов

Проверки реальной PostgreSQL находятся в `tests/integration` и включаются
тегом `integration`. Их помощники размещены в `*_test.go` того же каталога.

Если корневого `.env` ещё нет:

```powershell
Copy-Item .env-example .env
```

Заполните параметры подключения. Пример для локальной разработки:

```dotenv
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
POSTGRES_DB=chat
POSTGRES_USER=chat
POSTGRES_PASSWORD=YOUR_PASSWORD
POSTGRES_SSLMODE=disable
POSTGRES_TEST_DB=chat_test
STORAGE_DIR=storage/files
MAX_PHOTO_SIZE=5242880
```

Используйте фактические учётные данные development PostgreSQL вместо
`YOUR_PASSWORD`. В существующем `.env` достаточно добавить `POSTGRES_TEST_DB`:
адрес, порт, пользователь, пароль и SSL-режим общие с приложением.
Параметры хранилища также должны быть заполнены для общей загрузки конфигурации.
Файловые сценарии используют временные каталоги, а не пользовательские фото.

Имя тестовой базы обязательно, должно оканчиваться на `_test` и отличаться
от `POSTGRES_DB`. При неверной настройке или недоступной БД тесты завершаются
ошибкой, а не пропускаются. Автоматического перехода на development-базу нет.

Тесты читают корневой `.env` независимо от рабочей директории, включая GoLand.
Переменные окружения имеют приоритет, даже если они пустые.

Запустите PostgreSQL:

```powershell
docker compose --env-file .env -f docker/docker-compose.dev.yml up -d --wait postgres
```

Создайте тестовую базу один раз. Если она уже существует, команду пропустите:

```powershell
docker compose --env-file .env -f docker/docker-compose.dev.yml exec postgres createdb -U chat chat_test
```

Если меняли пользователя или имя тестовой базы, замените аргументы команды.
Другие инструкции по Docker находятся в [`docker/README.md`](../docker/README.md).

## Запуск integration-тестов

```powershell
go test -tags=integration -v -count=1 ./tests/integration
```

Тест подключения выполняет `SELECT 1` и проверяет закрытие пула. Миграционные
сценарии создают случайные схемы внутри тестовой БД и удаляют только их
после завершения. Механизм миграций проверяется фикстурами, а схема `users` —
применением настоящих SQL-файлов из `migrations/` и проверкой ограничений БД.
Тест repository применяет настоящие миграции в отдельной схеме и проверяет
сохранение и поиск пользователя, дубликаты username, повторяющиеся имена,
ошибки ограничений и отмену контекста.

Также проверяются миграции паролей и сессий, repository сессий,
атомарная регистрация и откат транзакции. HTTP-сценарии с настоящей БД
покрывают регистрацию, вход, доступ к собственному профилю и выход,
включая удаление сессии и сохранение остальных сессий пользователя.

Конкурентная регистрация одного username проверяется двумя goroutine:
одна операция успешна, другая получает ошибку занятого логина;
в БД остаются один пользователь и одна сессия.

Тест `app.Run` запускает настоящий HTTP-сервер с изолированной схемой БД
и проверяет подключение обработчиков и middleware в самом приложении.
Его сценарий фото включает загрузку JPEG, чтение владельцем и другим
пользователем, замену прозрачным PNG и сохранение фото при невалидной загрузке.
Проверяются запрет удаления без сессии, чужой сессией и с чужого origin,
очистка ссылки и файла при удалении, ответы `404` после удаления и повторное
удаление без изменения даты профиля.

Для проверки этого сценария отдельно:

```powershell
go test -tags=integration -run '^TestAppRunAuthentication$' -count=1 -v ./tests/integration
```

Тест команды миграций собирает CLI во временный каталог и запускает его
дважды: первый запуск применяет миграции, повторный не вносит изменений.
Для этого теста команда `go` должна быть доступна через PATH.

## Измерение покрытия

После подготовки тестовой PostgreSQL можно собрать общий отчёт
unit-, компонентных и integration-тестов. Команды для PowerShell:

```powershell
go test -tags=integration -count=1 '-coverpkg=./...' -coverprofile="$env:TEMP\chat-coverage.out" ./...
go tool cover -func="$env:TEMP\chat-coverage.out"
go tool cover -html="$env:TEMP\chat-coverage.out"
```

Кавычки вокруг всего `-coverpkg=./...` обязательны для корректной передачи
аргумента в PowerShell. Отчёт сохраняется во временном каталоге вне репозитория.
`-coverpkg` учитывает выполнение кода других пакетов, в том числе repository
из integration-тестов. Итоговую долю покрытия показывает строка `total`
в выводе `go tool cover -func`; проценты отдельных тестовых запусков
при общем `-coverpkg` не являются покрытием соответствующего пакета.

CLI миграций запускается отдельным процессом без инструментации покрытия:
его успешное выполнение проверяется тестом, но не учитывается в обычном
`coverprofile` родительского теста. Низкий процент команды сам по себе
не означает отсутствия проверки этого сценария.

Покрытие показывает выполненные операторы, а не полноту сценариев и утверждений.
Новые тесты добавляются для значимых правил и отказов; код не усложняется
ради достижения формальных 100%.

## Форматирование и статические проверки

```powershell
gofmt -w .
go vet ./...
go vet -tags=integration ./tests/integration
```

CI запускает оба набора тестов с `-race`; workflow описан в
[`CONTRIBUTING.md`](CONTRIBUTING.md#ci). Для локального запуска race detector
на Windows дополнительно нужен поддерживаемый C-компилятор.
