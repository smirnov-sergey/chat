# Future Design

Этот документ сохраняет идеи и возможные направления развития Chat. 
Он не заменяет описание текущей реализации и не является списком ближайших задач.
Разделы кратко фиксируют существующий baseline только там, где без него нельзя понятно отделить уже принятое решение от будущей возможности.

Продуктовое видение изложено в `vision.md`. Текущий статус и порядок разработки — в `ROADMAP.md`.
Здесь фиксируются варианты, которые стоит учитывать при принятии будущих решений, но не нужно реализовывать заранее.

## Аватар

Backend загрузки, замены, получения и удаления единственного фото реализован.
Действующие правила находятся в `DOMAIN_MODEL.md`, HTTP-контракт — в `openapi.yaml`.
Для будущего интерфейса без фотографии предполагаются инициалы или стандартное
изображение; frontend пока не реализован.

## Список переписок

Пагинация отложена до подтверждённой необходимости: текущий объём позволяет
получать весь список. При изменении сортировки на последнюю активность нужно
отдельно определить обновление списка и, если потребуется, курсор пагинации.

## Удаление аккаунта

Отложено до отдельного проектирования: нужно определить судьбу сообщений,
username, сессий и возможность восстановления. `deleted_at` пока не добавляется.

## Сообщения: проект хранения для этапа 8

Это проект решения, ещё не реализованная схема. Правила поведения находятся
в `DOMAIN_MODEL.md`. При завершении главы описание реализации переносится
в `ARCHITECTURE.md`.

Таблица `conversations_messages`:

| Поле | Тип и ограничения | Назначение |
| --- | --- | --- |
| `id` | BIGINT GENERATED ALWAYS AS IDENTITY, PK | ID сообщения и порядок внутри переписки |
| `conversation_id` | BIGINT NOT NULL, FK → conversations.id | Переписка |
| `sender_user_id` | BIGINT NOT NULL, FK → users.id | Отправитель |
| `client_message_id` | UUID NOT NULL | Идентификатор отправки клиента |
| `text` | TEXT NOT NULL, CHECK char_length(text) BETWEEN 1 AND 4000 | Текст сообщения |
| `created_at` | TIMESTAMPTZ NOT NULL | Дата, заданная приложением |

Уникальность `(conversation_id, sender_user_id, client_message_id)` защищает
от дублей. Индекс `(conversation_id, id)` обслуживает историю. Отдельный индекс
по дате не нужен. Внешние ключи без каскадного удаления.
Отправитель ссылается на пользователя, а не на строку участия: будущий выход
из группы не должен требовать удаления его сообщений. Проверка участия выполняется
при отправке и чтении. Пробельный текст запрещает service; CHECK проверяет длину.

### Транзакция отправки

`ConversationMessageRepository` выполняет SQL, `ConversationMessageStore`
управляет транзакцией по принятому в проекте образцу.

1. Начать транзакцию с уровнем READ COMMITTED.
2. Заблокировать строку переписки через `SELECT ... FOR NO KEY UPDATE`.
3. Отдельным запросом проверить участие текущего пользователя.
4. Найти сообщение по переписке, отправителю и клиентскому UUID.
   При совпадении текста вернуть исходное сообщение; при различии — конфликт.
5. Если повтора нет, вставить сообщение и получить его ID.
6. Зафиксировать транзакцию и только после этого вернуть успешный результат.

При ошибке транзакция откатывается. Проверки текста и UUID выполняются до неё.
Все пути записи сообщения должны соблюдать этот порядок; будущие операции
изменения состава также должны сначала блокировать строку переписки.
Так проверка участия не разойдётся с одновременным исключением пользователя.

Блокировка удерживается до конца транзакции. Она упорядочивает отправки
только внутри одной переписки и не мешает обычному чтению истории.
Разные переписки записываются независимо. Это ограничивает пропускную способность
одного чата, но подходит для небольших команд и упрощает гарантии порядка.
Свойства блокировки описаны в [документации PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS).

Один ID без блокировки недостаточен: транзакция с ID 11 может завершиться раньше
транзакции с ID 10. Читатель увидит 11, начнёт читать старые страницы и может пройти
место ещё невидимого сообщения 10. Блокировка берётся до INSERT и выдачи ID:
следующая отправка в этой переписке ждёт завершения предыдущей.
Identity использует стандартный CACHE 1; увеличение кеша последовательности
потребует пересмотра этой гарантии. Пропуски ID допустимы, общей непрерывной
нумерации или порядка между разными переписками не обещаем.

### История

`GET /conversations/{id}/messages?limit=50&before_id=123`.
Без `before_id` возвращается последняя страница. С ним добавляется условие
`id < before_id`; сортировка — `id DESC`. Курсор — положительный int64,
граница диапазона в выбранной переписке, а не отдельный ресурс для проверки доступа.

Выбираем `limit + 1` строку, возвращаем не больше `limit`. Если есть ещё строка,
`next_before_id` равен ID последнего возвращённого сообщения; иначе — `null`.
Ответ содержит `messages` (в том числе `[]`) и `next_before_id`.
Новые сообщения не сдвигают старые страницы; для получения новых клиент
пока заново запрашивает первую страницу. Это не механизм realtime-доставки.
