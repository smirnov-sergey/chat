# Roadmap

Roadmap показывает текущее состояние и план этапов. Подробно прорабатываем
только ближайший пункт; дальние этапы уточняем по мере разработки.

## Текущее состояние

Работает локальный HTTP-сервер с `GET /health`, корректной остановкой
и конфигурацией через окружение и `.env`. Есть тесты HTTP, конфигурации
и жизненного цикла сервера. Есть Swagger UI и черновая документация.
Добавлен development Compose для приложения и PostgreSQL с обновлением
Go-кода через Compose Watch. Проверены сборка, HTTP-ответ,
обновление через Watch, штатная остановка и сохранность данных.
Добавлено подключение Go к PostgreSQL через `database/sql` и `pgx`:
проверка связи при запуске с таймаутом и закрытие пула после HTTP-сервера.
Тесты, включая реальное подключение к PostgreSQL, пройдены.
Добавлена отдельная команда SQL-миграций на goose с блокировкой одновременных
запусков и integration-тестами на отдельной БД. Тесты миграций и `go test ./...`
пройдены, включая конкурентный запуск, повторное применение и откат при ошибке SQL.
Добавлен GitHub Actions workflow для проверки `gofmt`,
`go vet`, тестов с race detector и временной PostgreSQL, а также `govulncheck`.
Первый запуск workflow на GitHub ещё не подтверждён.
Добавлена миграция `users` с ограничениями и integration-тестами настоящей схемы.
Тесты миграции пройдены. Добавлены структура пользователя и repository
с созданием и точным поиском по username; новые integration-тесты ожидают запуска.
Создание пользователей через HTTP, переписки и веб-интерфейс ещё не реализованы.

**Активный этап: 3. Пользователь.**
**Ближайшая часть: проверка repository, затем валидация и service создания пользователя.**

## Этап 4. Регистрация и вход

Результат: пользователь регистрируется, входит, получает собственную
идентичность на сервере и выходит. Клиент не может выдать себя за другого пользователя.

- [ ] Определить правила регистрации, способ аутентификации и срок действия сессии.
- [ ] Реализовать безопасное хранение и проверку паролей
  в соответствии с выбранным способом входа.
- [ ] Добавить HTTP-регистрацию: ограничения ввода, контракт и тесты API.
- [ ] Реализовать вход и хранение сессий, обработку неверных учётных данных.
- [ ] Добавить проверку сессии на HTTP-границе и получение текущего пользователя.
- [ ] Реализовать выход, истечение и отзыв сессий.
- [ ] Добавить ограничения частоты попыток входа и регистрации,
  проверить cookie-настройки и защиту от CSRF, если используются cookies.
- [ ] После регистрации и входа отдельно спроектировать и добавить необязательный
  аватар профиля; направление описано в `FEATURE_DESIGN.md`.

Результат: Chat можно воспроизводимо установить и использовать вне компьютера разработчика.
Необходимые проверки безопасности выполняются и в предыдущих главах,
а не откладываются до этой главы.

- [ ] Настроить CI: форматирование, unit- и integration-тесты,
  `go vet` и race detector в Linux. Можно выполнить раньше, когда готова тестовая БД.
  Workflow добавлен; пункт закрывается после успешного запуска на GitHub.
- [ ] Подготовить production Docker-сборку и совместный запуск
  приложения, frontend и PostgreSQL.
- [ ] Настроить HTTPS и reverse proxy, проверить cookies,
  ограничения запросов и работу транспорта событий.
- [ ] Добавить необходимые для диагностики структурированные логи
  без паролей, токенов и содержимого личной переписки.
- [ ] Описать и проверить резервное копирование, восстановление
  базы и обновление приложения с миграциями.
- [ ] Развернуть приложение и провести сквозную проверку:
  вход, личная и групповая переписка, переподключение и перезапуск сервера.

## Границы плана

В этот план не входят вложения, звонки, каналы, боты, мобильные приложения,
сквозное шифрование, статусы прочтения и поиск по сообщениям.
Их не реализуем заранее. План не является обязательством вместить все
главы в полгода: объём корректируется по фактическому темпу и пониманию материала.
Первый полезный результат — личная переписка через веб-интерфейс;
следующие результаты — доставка событий, группы и развёртывание.
