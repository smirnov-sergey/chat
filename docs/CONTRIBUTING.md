# Contributing

Документ описывает правила разработки проекта Chat.

Главная цель — поддерживать единый стиль кода и архитектуры.

---

# Основные принципы

При написании кода придерживаемся следующих правил:

- простота важнее абстракций;
- явные зависимости;
- минимальная магия;
- читаемый код;
- предпочтение стандартной библиотеке Go;

# Интерфейсы

Интерфейсы создаются только тогда, когда они действительно нужны.

Правила:

- интерфейс объявляется в пакете, который его использует;
- не создавать интерфейсы "на будущее";
- избегать избыточных абстракций;
- разные потребители могут объявлять разные интерфейсы для одной конкретной реализации;
- интерфейс должен содержать только методы, которые вызывает его пакет;
- общий интерфейс не расширяется методом только потому, что он нужен другому потребителю.

# Тестирование

Каждая новая функциональность должна сопровождаться тестами.

- unit-тесты проверяют изолированную логику;
- integration-тесты проверяют взаимодействие компонентов, включая HTTP-границу;
- тесты должны проверять конкретный сценарий и быть независимыми друг от друга.

Состав integration-тестов и используемая тестовая инфраструктура определяются
вместе с реализацией соответствующей функции. Пока конкретное хранилище и CI
не выбраны, этот документ не предписывает тестовую СУБД или отдельные CI jobs.

Для конкурентной логики нужны тесты, которые действительно выполняют
конкурирующие операции; запуск race detector сам по себе таких сценариев не
создаёт. Fuzz-тесты уместны для критичных парсеров и других границ недоверенного
ввода. Конкретные команды и CI-проверки определяются при появлении этих частей
приложения.

Перед завершением backend-изменений запускаются `gofmt` и `go test ./...`;
`go vet ./...` — когда он уместен для изменения.

# Fake реализации

### Test doubles

- тестовые реализации размещаются только в `*_test.go` файлах;
- тестовая реализация находится в пакете, который потребляет интерфейс;
- тестовые типы и конструкторы должны быть неэкспортируемыми;
- fake не должен становиться частью production API;
- fake должен воспроизводить значимое поведение реальной реализации,
  включая доменные ошибки;
- для проверки соответствия интерфейсу рекомендуется использовать
  compile-time assertion.

# Коммиты

Формат сообщений:

```
feat: #XXXX - description
fix: #XXXX - description
refactor: #XXXX - description
test: #XXXX - description
chore: #XXXX - description
```

Каждый коммит должен выполнять одну логическую задачу.

После появления frontend допускается необязательный scope:

```
feat(frontend): #XXXX - description
fix(frontend): #XXXX - description
test(frontend): #XXXX - description
refactor(frontend): #XXXX - description
```

Для backend-only изменений аналогично может использоваться scope `backend`.
Сквозные и организационные изменения сохраняют короткую форму без scope,
например `chore: #XXXX - update project documentation`. Нумерация остаётся
общей для всего репозитория. Пробел между типом и scope не ставится;
`feat (front)` не используется.

Scope описывает область изменения, но не заменяет тип коммита. Он применяется
только тогда, когда действительно помогает отличить frontend- и backend-работу.

# Frontend

Frontend развивается по тем же правилам, что и backend: сначала сценарий и
архитектурная граница, затем небольшое законченное изменение, тестирование,
code review и актуализация документации.

- TypeScript используется в strict режиме;
- Vue-компоненты отвечают за представление и пользовательское взаимодействие,
  а работа с HTTP не размазывается по шаблонам;
- backend остаётся источником истины для бизнес-правил и валидации;
- frontend-валидация улучшает пользовательский опыт, но не заменяет проверок
  backend;
- состояние поиска, фильтров, сортировки и пагинации, которое определяет
  отображаемую страницу, по возможности отражается в URL;
- глобальное состояние вводится только для действительно разделяемых данных;
- сторонняя библиотека добавляется после появления задачи, которую неразумно
  решать средствами Vue, TypeScript, браузера или уже подключённых инструментов;
- недоверенные строки выводятся как текст; `v-html` и аналогичные raw HTML
  sinks не используются без отдельной модели доверия и санитизации;
- изменение публичного API сначала отражается в `openapi.yaml`, после чего с
  ним синхронизируется frontend-клиент;

Для frontend применяются тесты соответствующего уровня:

- unit-тесты — для чистой логики и преобразований;
- component-тесты — для поведения отдельного компонента;
- integration-тесты — для взаимодействия нескольких frontend-компонентов и HTTP-границы;
- end-to-end тесты — для небольшого набора критичных пользовательских сценариев в браузере;

Не требуется дублировать одну и ту же проверку на каждом уровне. Конкретный
набор инструментов, пороги покрытия и обязательные browser-сценарии описаны в
[`FRONTEND_DESIGN.md`](FRONTEND_DESIGN.md#тестирование) и поддерживаются
единообразно.

# Внешние зависимости и цепочка поставки

Стандартная библиотека Go, возможности Vue и browser API предпочтительнее
новой зависимости, если они адекватно решают задачу. Новая зависимость должна
решать конкретную проблему, а не добавляться ради удобства или демонстрации
инструмента.

Перед изменением `go.mod`, `go.sum`, `package.json`, `package-lock.json`,
GitHub Action SHA или Docker image digest проверяются:

- точное имя пакета по официальной документации проекта, чтобы исключить
  typosquatting и пакет-двойник;
- официальный владелец и репозиторий;
- назначение и необходимость зависимости;
- активность поддержки и история релизов;
- неожиданные смены владельца или maintainer;
- release notes и фактический diff обновления;
- lifecycle/install scripts и транзитивные зависимости;
- известные security advisory и лицензия;
- результаты соответствующих локальных проверок и CI;

Популярный registry, рекомендация AI-инструмента, lock-файл, checksum или digest
не являются доказательством добросовестности автора. Они помогают получить те
же байты повторно, но решение доверять этим байтам принимает разработчик.
Dependabot PR не сливается автоматически и проходит тот же review.

Пакет не устанавливается только ради его изучения. Сначала проверяются
официальный репозиторий, metadata registry, manifest, лицензия и опубликованный
исходный код. Команда установки выполняется только после решения добавить
зависимость. AI-инструмент не может принять это решение вместо разработчика.

Политика установки frontend-зависимостей, включая выполнение install scripts,
будет определена вместе с выбором frontend-инструментов.

# Документация

Документация обновляется вместе с изменением, которое делает её неактуальной.
Не требуется изменять каждый документ в каждом коммите: обновляется только
соответствующий источник истины.

- изменение понятий, отношений или бизнес-инвариантов отражается в `DOMAIN_MODEL.md`;
- изменение направлений зависимостей и ответственности компонентов отражается в `ARCHITECTURE.md`;
- изменение публичного HTTP-контракта отражается в `openapi.yaml`;
- изменение установки, конфигурации или обслуживания отражается в эксплуатационной документации;
- значимое архитектурное решение с долгосрочными последствиями рассматривается для отдельного ADR;
- текущее состояние, будущие направления и завершённые этапы продукта отражаются в `ROADMAP.md`;
- заметные пользовательские и эксплуатационные изменения выпусков отражаются в `CHANGELOG.md`.

Документ не создаётся заранее без содержательного назначения. Одна и та же
информация не дублируется в нескольких источниках истины.

## Проверка перед новой главой

Перед проектированием новой главы необходимо проследить существующий сценарий
от доменной модели и хранения до HTTP API и frontend. Анализ должен ответить на
следующие вопросы:

1. Описана ли возможность или её инварианты в `DOMAIN_MODEL.md`?
2. Какие данные уже хранятся и кто их изменяет?
3. Как существующее состояние проходит через Repository, Service или Processor?
4. Что уже возвращает публичный HTTP API?
5. Что уже показывает или позволяет сделать frontend?
6. Какой конкретный пользовательский сценарий отсутствует или работает неверно?

Если существующий механизм уже решает задачу, новая глава не создаётся. Если
недостаток найден, в проектировании фиксируются его конкретное проявление и
минимальный объём изменений, а не только желаемая техническая конструкция.

# Code Review Checklist

Перед коммитом необходимо убедиться, что:

- архитектура не нарушена;
- новая функциональность протестирована;
- отсутствует дублирование кода;
- используются доменные ошибки;
- соблюдено принятое в проекте правило загрузки конфигурации;
- нет глобальных зависимостей;
- влияние изменения на границы безопасности рассмотрено;
- `go test ./...` проходит успешно;
- OpenAPI поддерживается актуальным;
- соответствующая документация обновлена, если изменились контракт, поведение,
  модель предметной области, архитектура или эксплуатация системы.

# Главное правило

> Если решение можно сделать проще — нужно сделать проще.

Предпочтение всегда отдаётся понятному и поддерживаемому коду, а не сложным абстракциям.
