# Domain Model

Документ описывает предметную область Chat: основные понятия, отношения между ними, жизненные циклы и действующие бизнес-инварианты.

Здесь фиксируется смысл системы, а не способ её реализации. 
SQL-схема, структура Go-пакетов и HTTP endpoints описываются соответственно в migrations, `ARCHITECTURE.md` и `openapi.yaml`.

Документ фиксирует согласованные правила предметной области.
Статус реализации указывается отдельно: согласованное правило не означает,
что соответствующая возможность уже работает.
Отложенные возможности и идеи находятся в `FEATURE_DESIGN.md`, порядок работ — в `ROADMAP.md`.

---

# Назначение Chat

Chat предназначен для прямых диалогов, личной переписки с собой («Избранное»)
и небольших групповых переписок.
Пользователь получает доступ только к перепискам, участником которых является.

# Пользователь

**Статус: реализованы регистрация, вход, выход и чтение собственного профиля
через HTTP API, а также загрузка, замена, получение и удаление фото профиля.
Изменение имени и удаление аккаунта пока не реализованы.**

| Поле | Назначение |
| --- | --- |
| `id` | Постоянный внутренний идентификатор пользователя |
| `username` | Уникальный неизменяемый логин для входа и поиска собеседника |
| `name` | Имя в интерфейсе, может изменяться и повторяться |
| `password_hash` | Хеш пароля; не возвращается клиенту |
| `photo` | Необязательная ссылка на единственное текущее фото профиля |
| `created_at` | Время создания аккаунта |
| `updated_at` | Время последнего фактического изменения данных профиля |

## Username

- Пробелы по краям удаляются, буквы приводятся к нижнему регистру.
- После нормализации допускается от 3 до 32 символов: `a–z`, `0–9`, `_`.
- `Ivan` и `ivan` обозначают один логин.
- В первой версии username неизменяемый.
- Занятый логин отклоняется. Уникальность должна обеспечиваться и при
  одновременных запросах; в миграции добавлено уникальное ограничение PostgreSQL.

## Имя (`name`)

- Обязательно передаётся при создании пользователя отдельно от username.
- Совпадения с чужими именами допустимы. Изменение имени предусмотрено правилами,
  но соответствующий сценарий ещё не реализован.
- Пробелы по краям удаляются. После этого длина — от 1 до 80 Unicode-кодовых
  точек (`rune`); составной emoji может занимать несколько таких символов.
- Кириллица и emoji разрешены; переносы строк и управляющие символы запрещены.
- Регистр и пробелы внутри имени сохраняются. Нормализация выполняется перед
  валидацией; строка из одних пробельных символов отклоняется как пустая.

## Даты и идентичность

- `id`, `username` и `created_at` неизменяемы.
- Время задаёт сервер; клиент не передаёт значения дат.
- При создании `created_at` и `updated_at` равны.
- `updated_at` обновляется при фактическом изменении данных профиля.
  Повторное сохранение того же `name` дату не меняет.
- Вход, чтение и отправка сообщений не обновляют `updated_at`.
- Даты обозначают моменты времени; в API передаются в UTC.

## Регистрация и вход

Пользователь регистрируется самостоятельно и входит по username и паролю.
Обязательных email и телефона нет.

- При регистрации обязательны username, имя и пароль.
- Новый пароль содержит 15–128 Unicode-кодовых точек; обязательных классов
  символов нет. Пароль не обрезается, не меняет регистр и не нормализуется.
- При входе допускается пароль длиной 1–128 Unicode-кодовых точек:
  минимальная длина нового пароля не применяется к проверке существующего.
- Пароль хранится только в виде хеша Argon2id с индивидуальной случайной солью.
- Пользователь и первая сессия создаются одной транзакцией.
  Если создать сессию не удалось, регистрация откатывается целиком.
- Успешный вход создаёт новую сессию, не отменяя предыдущие.
- Неизвестный username, неверный пароль и отсутствие пароля у старой записи
  дают одну ошибку входа. Для неизвестного пользователя и записи без пароля
  также выполняется Argon2, чтобы убрать основной быстрый путь отказа.
  Это не гарантирует одинаковое время ответа.
- Чтение профиля пока разрешено только его владельцу, определённому по сессии.

Изменение и восстановление пароля пока не реализованы.

## Сессия

- Сессия принадлежит одному пользователю; у пользователя может быть несколько сессий.
- Срок действия — 7 дней с создания, без продления по активности.
- Клиент получает случайный токен в cookie `chat_session`; в БД хранится
  только SHA-256-хеш токена, идентификатор пользователя и даты создания и истечения.
- Истёкшая или отсутствующая в БД сессия не даёт доступа к профилю.
  Автоматическое удаление истёкших записей пока не реализовано.
- Выход удаляет только сессию из переданной cookie и очищает cookie.
  Другие сессии пользователя сохраняются.
- Повторный выход, отсутствие cookie и недействительный токен считаются
  успешным выходом. При ошибке удаления из БД cookie не очищается.

Ограничения частоты запросов и HTTP-настройки описаны в `openapi.yaml`;
механизм защиты и границы его применения — в `ARCHITECTURE.md`.

## Фото профиля

- Фото необязательно; отсутствие фото не мешает регистрации и входу.
- У пользователя не больше одного текущего фото. История и оригиналы не хранятся.
- Загружать, заменять и удалять фото может только владелец профиля.
  Получать фото любого пользователя может любой пользователь с действующей сессией.
- Принимаются JPEG и PNG; размер файла ограничен настройкой сервера,
  ширина и высота — от 1 до 4096 пикселей.
- Результат — центральный квадрат 256 × 256 в PNG с сохранением прозрачности;
  небольшие изображения увеличиваются. Метаданные оригинала не переносятся,
  EXIF-ориентация не учитывается.
- При создании аккаунта фото отсутствует. Замена и удаление установленного фото
  обновляют `updated_at`; чтение и повторное удаление отсутствующего фото — нет.
- Отсутствие фото обозначается `NULL`, пустая ссылка запрещена.

Удаление аккаунта отложено; поле `deleted_at` пока не добавляется.

# Переписка

**Статус: реализованы создание прямого диалога по username, чтение переписки
участником и получение списка собственных переписок через HTTP API.
Также реализованы личная переписка с собой, отправка сообщений и чтение истории.
Группы ещё не реализованы.**

Переписка — самостоятельная сущность с постоянным ID, типом и датой создания.
Участие связывает пользователя с перепиской; один пользователь не может быть
добавлен в одну переписку несколько раз. Сообщения принадлежат
переписке независимо от её типа.

| Тип | Назначение | Участники и уникальность |
| --- | --- | --- |
| `personal` | Личная переписка с собой, «Избранное» | Один участник; одна переписка на пользователя |
| `direct` | Прямой диалог | Два разных участника; одна переписка на неупорядоченную пару пользователей |
| `group` | Групповая переписка | Несколько участников; одинаковый состав не делает группы одной перепиской |

Групповая переписка — будущая возможность. Правила групповых ролей,
изменения состава и доступа к истории будут определены отдельно.

## Прямой диалог

- Авторизованный пользователь начинает диалог по точному username собеседника.
  Применяются существующие правила нормализации username; поиск по части
  строки и общий каталог пользователей в этот этап не входят.
- Собеседник должен существовать. Создание прямого диалога с собой запрещено:
  для этого предусмотрен отдельный тип `personal`.
- Подтверждение собеседника не требуется. Созданная переписка сразу доступна
  обоим участникам и видна в их списках, даже если сообщений ещё нет.
- Порядок участников не имеет значения. Повторное создание возвращает
  существующий диалог без изменения его ID и даты создания.
- Одновременные запросы, в том числе встречные, не создают дубликаты.
  Переписка создаётся целиком вместе с обоими участниками либо не создаётся.
- Состав прямого диалога и его тип не изменяются. Удаление диалога,
  выход из него и блокировки в текущий этап не входят.
- Дату создания задаёт сервер; в API она передаётся в UTC.

## Личная переписка («Избранное»)

**Статус: создание, чтение и включение в общий список реализованы.**

- Тип — `personal`. Пользователь является владельцем и единственным участником.
- У пользователя не больше одной личной переписки. Она создаётся при первом
  явном обращении за «Избранным», а не при регистрации или чтении общего списка.
- Повторные и одновременные запросы возвращают ту же переписку с прежними ID
  и датой создания. Личная переписка и её участие создаются атомарно.
- После создания «Избранное» входит в общий список владельца, даже без сообщений.
  Оно подчиняется общей сортировке и не закрепляется сверху автоматически.
- Читать переписку может только владелец. Для постороннего действует общее
  правило «не найдено»; добавить другого участника нельзя.
- Удаление, выход и изменение типа не предусмотрены в этой главе.
- Сообщения в «Избранном» используют общий механизм отправки и истории.

## Доступ и список переписок

- Пользователь видит только переписки, участником которых является.
- При запросе отдельной переписки посторонний пользователь получает тот же
  результат «не найдено», что и при запросе несуществующей переписки.
- Список выдаётся целиком, без пагинации, от новых переписок к старым: по дате создания
  по убыванию, а при одинаковой дате — по ID по убыванию.
- Чтение и повторное создание не меняют положение переписки в списке.
  Сортировка по последнему сообщению не входит в этап 6.

Отправка сообщений и чтение истории реализованы в этапе 8.

## Сообщения и история

**Статус: отправка и чтение истории реализованы через HTTP API.**

- Сообщение принадлежит переписке и имеет отправителя. Отправитель определяется
  по сессии; клиент не может отправить сообщение от имени другого пользователя.
- Отправлять сообщения и читать историю может только участник переписки.
  Чужая и отсутствующая переписки дают одинаковый `404`.
- Правила одинаковы для `direct` и `personal`. Общий механизм должен применяться
  и к будущим группам; правила вступления и доступа к старой истории определяются
  отдельно в главе групп.
- Первая версия поддерживает только обычный текст: без вложений, форматирования,
  редактирования и удаления. Текст сохраняется как передан, включая переносы строк.
  Пустой текст и текст только из пробельных символов запрещены.
- Лимит — 4000 Unicode-кодовых точек (`rune` в Go), включая пробелы
  и переносы строк. Некорректный UTF-8 и U+0000 запрещены. Это не число байтов и не число
  визуальных символов: один символ с модификаторами может занимать несколько rune.
- Дату задаёт сервер. Успешный ответ означает, что сообщение сохранено в PostgreSQL;
  он не означает доставку или прочтение собеседником.
- Каждый успешный POST создаёт новое сообщение и возвращает `201`.
  Защиты от повторной отправки нет. При потере ответа результат неизвестен;
  ручной повтор может создать дубль. Будущий клиент не должен автоматически
  повторять отправку. Решение о защите от дублей отложено до разработки интерфейса.
- Порядок сообщений задаётся ID. Отправки в одну переписку сериализуются
  на сервере; дата назначается после получения блокировки. Даты могут совпадать,
  а серверные часы — корректироваться. Порядок нажатий на разных устройствах
  и порядок прихода HTTP-запросов не гарантируются.
- Первая страница содержит последние сообщения; следующие позволяют читать
  более старые. Размер страницы фиксирован — до 50 сообщений.
  Используется курсор, а не OFFSET. Внутри страницы сообщения идут от новых к старым.
  Пустая история возвращает пустой список. Чтение ничего не создаёт.
  Граница `before_id` исключительная; `next_cursor` передаётся в следующий запрос.
  На последней странице курсор равен `null`. Каждая страница читается отдельно,
  общего снимка истории между запросами нет.
- В этой главе список переписок сохраняет сортировку по дате создания.
  Поднятие по последнему сообщению, непрочитанные, статусы доставки и realtime
  требуют отдельных сценариев и пока не добавляются.
