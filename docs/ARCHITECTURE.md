# Architecture

Документ описывает фактическую архитектуру Chat: основные компоненты, их ответственность и направления зависимостей.

Цель — простая и понятная архитектура приложения без абстракций, для которых пока нет практической необходимости.

---

# Архитектурные принципы

При разработке проекта соблюдаются следующие принципы:

- явные зависимости и Dependency Injection;
- разделение HTTP, бизнес-логики и хранения данных;
- небольшие интерфейсы в пакетах-потребителях;
- композиция вместо наследования;
- минимальное количество глобального состояния;
- стандартная библиотека Go там, где она адекватно решает задачу;
- архитектурные решения исходят из существующих сценариев, а не из гипотетического будущего.

# Общая схема

## Топология продукта

В development Compose работают `app` (Go HTTP-сервер) и `postgres`.
HTTP-порт опубликован на `127.0.0.1:8080`; порт базы также доступен только
локально. Приложение запускается после готовности PostgreSQL и проверяет соединение.
Данные базы хранятся в named volume.

Compose Watch пересобирает образ при изменении Go-кода или файлов сборки.
Бинарник собирается в Dockerfile и запускается напрямую как основной
процесс контейнера. Неуспешная сборка не заменяет работающий контейнер.

## Внутренняя схема приложения

HTTP-сервер обслуживает проверку работоспособности, регистрацию, вход,
выход и чтение собственного профиля. Запрос проходит следующую цепочку:

```text
CrossOriginProtectionMiddleware
  -> AuthRateLimitMiddleware
  -> SessionMiddleware
  -> router
  -> UserHandler
  -> UserService / SessionService
  -> repository
  -> PostgreSQL
```

Service зависит от небольших интерфейсов нужных ему зависимостей, а конкретная
SQL-реализация находится в `internal/repository`. Модели и валидация не зависят
от HTTP и SQL. Зависимости связываются в `internal/app.Run`.

# Композиция приложения

`cmd/chat/main.go` загружает `.env` в окружение процесса,
получает конфигурацию через `internal/config`,
создаёт контекст сигналов и вызывает `internal/app.Run`.
`app.Run` настраивает HTTP-сервер, открывает TCP listener, собирает зависимости
и передаёт управление функции `serve` из `internal/app/server.go`.
Между открытием listener и запуском HTTP выполняется подключение к базе
через `internal/postgres.Open` с таймаутом 5 секунд. При ошибке listener закрывается.
Ошибки возвращаются до `main`, который завершает процесс с кодом 1.

`internal/router` регистрирует маршруты и получает только обработчики.
Middleware и сервисы в router не передаются. Все middleware собираются
в `app.Run` и оборачивают единый маршрутизатор.
`internal/handlers` содержит HTTP-обработчики, middleware, общую обработку
ошибок, чтение JSON и запись ответов. HTTP DTO находятся в `internal/dto`;
ответ профиля формируется явно и не содержит хеш пароля.
`internal/postgres` использует `database/sql` с драйвером `pgx/stdlib`.
`sql.DB` — пул соединений; `PingContext` проверяет фактическую связь с базой.
`internal/model/user` содержит структуру пользователя без поведения
и общие ошибки пользователя. Поле `PasswordHash` дополнительно исключено
из JSON через `json:"-"`.
`internal/repository.UserRepository` выполняет создание пользователя и поиск
по username или ID с контекстом вызывающего кода. Локальный интерфейс SQL-запросов
позволяет использовать как пул `*sql.DB`, так и транзакцию `*sql.Tx`.
ID генерирует PostgreSQL; `Create` заполняет его в переданной структуре только
после успешного INSERT с `RETURNING id`. Дубликат определяется через
`ON CONFLICT (username) DO NOTHING`. Отдельной проверки существования перед
вставкой нет. Прочие ошибки БД оборачиваются через `%w`.

`internal/service.UserService` реализует регистрацию, вход, чтение профиля
и выход. Нормализует поля, вызывает отдельные валидаторы и `internal/password`
для хеширования и проверки пароля. При регистрации задаёт одинаковые даты
создания и изменения в UTC.
`UserRegistrationStore` в repository создаёт пользователя и первую сессию
одной транзакцией, используя существующие repository. ID в переданных моделях
обновляются только после успешного commit.
Контекст вызывающей операции передаётся до `QueryRowContext`.
`SessionService` создаёт, проверяет и отзывает сессии через `SessionRepository`.
Логика переписки пока отсутствует.

Integration-тесты PostgreSQL и миграций находятся в `tests/integration`
и запускаются с тегом `integration`. Общая настройка БД и временных схем
находится в `*_test.go` этого каталога. Отдельного пакета тестовой инфраструктуры
в `internal` нет. Изолированные тесты находятся рядом с проверяемым кодом.

# Слои приложения

| Пакет | Ответственность |
| --- | --- |
| `internal/model/user` | Данные пользователя и общие ошибки |
| `internal/model/session` | Данные сессии, выдаваемый токен и ошибки |
| `internal/validation` | Проверка уже нормализованных полей без их изменения |
| `internal/service` | Бизнес-сценарии и интерфейсы нужных им зависимостей |
| `internal/repository` | SQL-запросы, чтение результатов и обработка ошибок хранения |
| `internal/handlers` | HTTP-обработчики, middleware, чтение запросов и запись ответов |
| `internal/router` | Регистрация маршрутов |
| `internal/dto` | HTTP-модели запросов и ответов |
| `internal/password` | Argon2id: хеширование и проверка паролей |
| `internal/app` | Композиция зависимостей и жизненный цикл HTTP-сервера |
| `internal/postgres` | Открытие и проверка пула соединений |
| `internal/config` | Загрузка и проверка конфигурации |
| `internal/migrate` | Применение SQL-миграций |

`model` — группирующий каталог; собственного Go-пакета в нём нет.
Repository разных сущностей могут использовать общие закрытые функции
своего пакета. Service и validation пока не делятся на подсистемы: такие
границы выделяются при появлении самостоятельных групп бизнес-сценариев.

## Аутентификация и защита HTTP

Пароли хешируются Argon2id: 19 MiB памяти, 2 итерации, параллелизм 1,
случайная соль 16 байт, результат 32 байта. Хеш хранится в формате PHC.
Проверка принимает только текущий профиль параметров; сравнение результата
выполняется через `subtle.ConstantTimeCompare`.

Токен сессии состоит из 32 случайных байт и передаётся в cookie в Base64url
без padding. В БД хранится SHA-256 исходных байт. Утечка таблицы сессий
не раскрывает исходные токены. Это не JWT.

Cookie имеет Path=/, HttpOnly, SameSite=Lax и Expires. Secure включён
по умолчанию; для локального HTTP отключается конфигурацией.
Правила сессии описаны в `DOMAIN_MODEL.md`, HTTP-контракт — в `openapi.yaml`.

Защита от межсайтовых запросов использует `http.CrossOriginProtection`.
Браузерные UI и API должны работать с одним origin; CORS не настроен.
Эта защита выполняется до ограничения частоты и проверки сессии.

Ограничитель учитывает IP соединения и отдельные фиксированные окна для входа
и регистрации. Счётчики защищены mutex, число записей ограничено, истёкшие
записи очищаются при запросах без фоновой goroutine. Алгоритм находится
в `internal/handlers/rate_limit.go`; HTTP middleware — в `middleware.go`.
Состояние локально для процесса, перезапуск его сбрасывает. Прокси-заголовки
не используются: перед развёртыванием за reverse proxy нужно отдельно определить
доверенные прокси и способ получения IP. Ограничитель не предотвращает
распределённый перебор с разных IP и не задаёт общий предел параллельных Argon2.

`SessionMiddleware` пропускает публичные пути health, регистрации, входа и выхода.
Для остальных путей проверяет cookie и сессию и помещает подтверждённый ID
пользователя в контекст запроса. Поэтому неизвестный путь без сессии получает
401 до маршрутизации. `UserHandler.GetByID` отдельно проверяет право на профиль:
ID из URL должен совпасть с ID из контекста; чужая запись из БД не читается.

Внутренние ошибки журналируются и преобразуются в общий ответ 500.
Известные ошибки отображаются в публичные статусы без технических подробностей.

# Миграции схемы

`cmd/migrate` — отдельная команда применения SQL-миграций. Она загружает
конфигурацию по тем же правилам, что и HTTP-сервер, открывает PostgreSQL
через `internal/postgres` и вызывает `internal/migrate.Up`.

`internal/migrate` использует provider API goose без глобального реестра.
Получает пул и `fs.FS` явно; не читает окружение и не закрывает переданный пул.
Каждая SQL-миграция по умолчанию транзакционная. Версии учитываются goose,
а session advisory lock PostgreSQL сериализует запуски мигратора в одной базе.
HTTP-сервер миграции не выполняет. Первая миграция создаёт таблицу `users`.

Правила файлов, команды и проверка на отдельной базе описаны в
[`migrations/README.md`](../migrations/README.md).

# Жизненный цикл приложения

После открытия TCP listener сервер выполняет `Serve` в отдельной goroutine.
Основная goroutine ожидает ошибку сервера или отмену контекста по `Ctrl+C`
либо `SIGTERM`. Результат `Serve` передаётся через канал с буфером 1.

При отмене контекста вызывается `Shutdown` с отдельным контекстом от
`context.Background()` и таймаутом 10 секунд. Контекст сигнала уже отменён,
поэтому использовать его для ожидания завершения запросов нельзя.
Контексты HTTP-запросов не наследуют контекст сигнала: активные запросы
получают возможность завершиться самостоятельно.

При ошибке `Shutdown` вызывается `Close` для принудительного закрытия
соединений. Перед возвратом функция дожидается результата `Serve`.
`http.ErrServerClosed` считается ожидаемым результатом остановки,
превышение таймаута — ошибкой. Принудительное закрытие соединений
не гарантирует завершение обработчиков, игнорирующих отмену контекста.

Логика проверяется тестами с локальными TCP-соединениями и отменой
контекста без сигналов ОС. Доставка сигналов проверяется вручную.
Пул PostgreSQL закрывается после возврата из `serve`, когда ожидание
активных HTTP-запросов завершилось. При ошибке запуска он также закрывается.
